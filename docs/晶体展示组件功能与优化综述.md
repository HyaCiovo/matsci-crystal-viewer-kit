# 晶体展示组件功能与优化综述

本文档面向 `matsci-crystal-viewer-kit` 的维护者、项目汇报使用者、软著材料整理者以及技术博客作者，系统总结当前晶体展示组件的：

1. 功能边界与能力结构
2. 已经落地的性能优化
3. 已经落地的展示与交互优化
4. 适合继续迭代的优化路线

本文强调“**已经实现并进入代码主路径**”的优化项，避免将规划项、实验项写成既成事实。

---

## 1. 组件定位

`matsci-crystal-viewer-kit` 本质上是一个：

- 以 **Scene JSON** 为输入的数据驱动晶体结构渲染运行时
- 以 **React + Three.js** 为基础的 3D viewer 组件包
- 具备工具栏、设置面板、图例面板、全屏、截图、导出等完整 viewer shell 的可复用组件

在 `material-search-portal` 中，它承担的是“材料结构详情的主 3D 展示组件”角色，而不是通用图形平台或搜索 UI。

其职责边界很清晰：

- 负责 Scene JSON 到可交互 3D 视图的渲染
- 负责原子、键、多面体、晶胞、坐标轴等对象的统一显示
- 负责选择、高亮、缩放、旋转、复位、导出等 viewer 行为
- 允许宿主注入设置面板、图例、导出行为和文案

它不负责：

- 后端查询
- 结构检索流程
- CIF/材料对象到 Scene JSON 的上游业务建模
- 页面级路由、权限、数据缓存等外层产品逻辑

## 2. 功能概览

### 2.1 核心渲染能力

组件当前支持以下结构对象类型进入统一场景：

- `spheres`：原子球
- `cylinders`：化学键 / 连线
- `lines`：晶胞线框
- `arrows`：坐标轴 / 矢量
- `convex`：配位多面体
- `surface`：表面对象
- `ellipsoids`：椭球对象
- `bezier`：曲线对象
- `labels`：标签对象

这些对象以 Scene JSON 的形式输入，统一通过 `buildSceneGraph()` 和 `ThreeBuilder.makeObject()` 进入 Three.js 场景。

对应核心实现位于：

- `src/components/crystal-toolkit/scene/Scene.ts`
- `src/components/crystal-toolkit/scene/scene-graph.ts`
- `src/components/crystal-toolkit/scene/three_builder.ts`
- `src/components/crystal-toolkit/scene/scene-types.ts`

### 2.2 Viewer 交互能力

当前已具备的主要 viewer 行为包括：

- 鼠标拖拽旋转
- 滚轮缩放
- 视角复位
- 对象点击选择
- 选中对象 outline 高亮
- 二级 inset 视图联动
- settings panel 开合
- 底部 legend 面板挂载
- 全屏/退出全屏
- PNG 截图导出
- GLTF / GLB / USDZ 等模型导出
- 宿主自定义导出菜单项

这些能力主要由以下模块协同实现：

- `SceneToolbar.tsx`
- `scene-interaction.ts`
- `selection-controller.ts`
- `scene-controls.ts`
- `sceneExport.ts`
- `inset-helper.ts`

### 2.3 宿主侧结构展示能力

在 `material-search-portal` 中，viewer 宿主层不仅仅是“把包接进来”，而是额外补齐了结构展示业务所需的完整能力：

- 支持服务端 Scene JSON 和浏览器本地 Scene 双路径
- 支持 unit cell 模式切换
- 支持 bonding algorithm 切换
- 支持颜色方案切换：Jmol / VESTA / CPK
- 支持半径模式切换：ionic / covalent / vdw / uniform
- 支持周期复制原子显示
- 支持多面体显示开关
- 支持晶胞、键、原子、坐标轴分组显隐
- 支持结构导出请求透传到宿主业务链路

宿主侧主组件位于：

- `material-search-portal/src/components/CrystalToolkitViewer.tsx`

## 4. 已实现的性能优化

这一节是本文的重点。以下内容均为**已进入当前代码主路径**的优化，不是待办事项。

### 4.1 全屏切换不再销毁并重建 Scene

#### 原问题

在早期实现中，全屏切换容易触发 mount 变化，进一步导致 Scene、renderer、controls、事件监听等底层对象重新创建。  
这类重建会带来：

- 画面闪烁
- 交互状态丢失
- resize 连锁抖动
- 不必要的对象分配和 GPU/CPU 重新初始化

#### 已实现优化

当前实现已经改成：

- 保留底层 `Scene` 实例
- 在容器变化后使用 `attachToMountNode()` 重新绑定 mount
- 调用 `resizeRendererToDisplaySize()` 同步尺寸
- 再调用 `renderScene()` 做一次稳定重绘

相关代码：

- `CrystalToolkitScene.tsx`
  - `expanded` 切换时调用 `scene.current.attachToMountNode?.(mountNode)`
  - 随后调用 `resizeRendererToDisplaySize()` 与 `renderScene()`
- `Scene.ts`
  - `attachToMountNode()`

#### 优化收益

- 全屏切换稳定性提升
- 避免 Scene runtime 重建
- 降低全屏切换的瞬时卡顿和闪烁概率
- 保留 selection、camera、controls 等运行态上下文

---

### 4.2 Resize 路径统一到 `ResizeObserver + Scene.resizeRendererToDisplaySize()`

#### 原问题

3D 结构 viewer 的尺寸变化来源很多：

- 父容器宽高变化
- 页面布局变化
- 全屏切换
- 浏览器窗口 resize

如果 React 层、window resize、viewer 内部各自维护一套 resize 行为，就会出现：

- 重复 resize
- 渲染抖动
- canvas 与 label renderer 尺寸不同步

#### 已实现优化

当前 `CrystalToolkitScene` 使用 `useResizeObserver` 监听 mount node 尺寸变化，并统一转发到：

- `scene.current.resizeRendererToDisplaySize()`

而 `Scene.resizeRendererToDisplaySize()` 内部统一完成：

- mount 尺寸同步
- label renderer 尺寸同步
- SVG renderer 尺寸同步
- WebGL renderer 缓冲区尺寸与像素比同步
- viewport/scissor 重设
- 必要时触发 `renderScene()`

相关代码：

- `CrystalToolkitScene.tsx`
- `sceneComponentShared.ts`
- `scene/Scene.ts`

#### 优化收益

- resize 来源被统一收敛
- 画布尺寸、标签层尺寸和主 viewport 保持一致
- 减少“容器变了但 3D 视图没有同步”这类问题

---

### 4.3 主 viewport 配置从“每帧执行”收敛为“初始化/resize 执行”

#### 原问题

WebGL 的 `setSize` / `setScissor` / `setViewport` 如果放在高频渲染路径中持续执行，会带来不必要的 CPU 开销，并放大多 viewport 场景下的状态切换成本。

#### 已实现优化

当前 `Scene.ts` 中新增了：

- `mainViewportConfigured`
- `syncMainViewport()`

并将主 viewport 初始化与更新收敛到：

- renderer 初始化阶段
- `attachToMountNode()`
- `resizeRendererToDisplaySize()`
- inset 渲染结束后的主 viewport 恢复

而 `renderScene()` 本身不再重复做主 viewport 配置。

#### 优化收益

- 减少每帧状态重设
- 降低 WebGL 渲染路径的固定开销
- 为后续更复杂的多 viewport / multi-pass 渲染打下更清晰的结构基础

---

### 4.4 Outline 高亮改为 dirty-driven 更新

#### 原问题

outline 高亮如果每一帧都无条件刷新，会造成：

- 多余的对象遍历
- 多余的 outline scene rebuild
- 在静态场景下仍然持续消耗 CPU

#### 已实现优化

当前 `Scene.ts` 中引入了：

- `outlineDirty`
- `refreshOutlineIfNeeded()`

只有在这些情况下才会刷新 outline：

- 选择状态变化
- 场景替换
- `toggleVisibility()` 导致选中对象不可见
- 需要恢复旧 selection

在普通渲染路径中只会调用 `refreshOutlineIfNeeded()`，但如果 `outlineDirty` 为 `false`，则不会真正重建 outline。

#### 优化收益

- 显著减少静态帧中的 outline 维护成本
- 让 selection 高亮从“帧驱动”切换为“状态驱动”

---

### 4.5 `toggleVisibility` 与 selection 清理联动

#### 原问题

如果对象被隐藏，但 selection 状态仍然残留，会导致：

- outline 残留
- inset 与主场景状态不一致
- 选中对象逻辑与实际可见对象不一致

#### 已实现优化

`Scene.toggleVisibility()` 当前不仅负责设置 `obj.visible`，还会：

- 调用 `selectionController.removeInvisibleSelections(...)`
- 在必要时将 `outlineDirty = true`
- 再执行一次稳定 `renderScene()`

#### 优化收益

- 减少无效 outline
- 保证显示状态与选择状态一致
- 避免隐藏/显示切换后视图出现“逻辑脏状态”

---

### 4.6 Scene 结构图构建与运行时职责拆分

#### 原问题

过去 `Scene.ts` 同时承担：

- 场景生命周期
- Three 对象构造
- 命中测试
- 交互
- 选择
- inset
- debug

这会导致：

- 文件过大
- 修改局部逻辑时容易引入回归
- 单模块 cognitive load 过高

#### 已实现优化

当前运行时已经完成显著模块化：

- `buildSceneGraph()` 负责 JSON 到 scene tree 的编排
- `scene-object-registry.ts` 负责对象注册与可点击对象维护
- `scene-hit-test.ts` 负责命中测试
- `scene-interaction.ts` 负责 DOM 事件与点击/悬停桥接
- `selection-controller.ts` 负责 selection 状态与 outline scene
- `scene-camera.ts` 负责视角 framing
- `scene-controls.ts` 负责 Orbit / control 行为

#### 优化收益

- 降低后续维护成本
- 更容易做针对性性能优化
- 更容易在具体模块上做 profiling 与替换

这类“结构性优化”不是直接提升 1 帧性能，但它极大提升了后续优化的可实施性，是非常关键的一类长期收益。

---

### 4.7 类型与 fixture 依赖解耦

#### 原问题

运行时代码依赖大 fixture 文件会带来两个问题：

- 模块边界不清晰
- 运行时代码与示例数据耦合，影响打包分析与维护

#### 已实现优化

当前 Scene 类型已经抽离到：

- `src/components/crystal-toolkit/scene/scene-types.ts`

同时示例/fixture 数据迁移到了：

- `src/components/crystal-toolkit/fixtures/*`

运行时代码改为从独立类型文件导入，不再从大示例文件中拿类型定义。

#### 优化收益

- 降低运行时代码对 fixture 的耦合
- 让打包边界更清晰
- 为后续 tree shaking 和产物瘦身打基础

---

### 4.8 宿主侧 Scene 视觉加工改为“轻量变换层”，避免重复重建拓扑

#### 原问题

颜色方案、半径模式、多面体透明度等视觉变化，如果每次都重新完整生成 Scene 拓扑，会产生不必要的 CPU 开销。

#### 已实现优化

宿主侧当前将 Scene 生成流程拆成两层：

1. **结构拓扑层**
   - `buildCrystalToolkitScene()`
2. **视觉变换层**
   - `applySceneVisuals()`
   - `transformSceneJsonForViewer()`

也就是说：

- bonds / atoms / polyhedra 的结构构建与
- 颜色重映射 / sphere scale / opacity 调整

已经被明确拆开。

#### 优化收益

- 视觉参数变化时尽量避免重跑完整拓扑构建
- 让“结构变化”和“视觉变化”成为两个不同层级的问题
- 有利于后续继续做 memo、缓存与增量更新

---

### 4.9 宿主侧高频可见性和配色切换使用 `useMemo + startTransition`

在 `material-search-portal` 中，viewer 的宿主层对一些高频交互做了 React 层优化：

- 多个派生数据使用 `useMemo`
- 配色模式、半径模式、显示重复原子等设置切换使用 `startTransition`

相关代码：

- `material-search-portal/src/components/CrystalToolkitViewer.tsx`

#### 优化收益

- 减少同步阻塞更新
- 让部分“非紧急视觉切换”交给 transition 执行
- 在复杂场景下改善设置切换时的主线程卡顿体感

---

### 4.10 视图区域滚轮缩放与页面滚动分离

#### 原问题

浏览器默认滚轮很多场景是 passive 的，用户在 3D 区域滚轮操作时，页面可能先滚动，导致：

- 缩放手感差
- 页面误滚
- viewer 与页面滚动竞争

#### 已实现优化

宿主侧在 `sceneShellRef` 上挂了 non-passive `wheel` 监听，并仅在 `scene-frame` 区域内 `preventDefault()`，同时避免拦截 settings panel / menu panel 的滚动。

#### 优化收益

- 3D 视图滚轮行为更稳定
- 降低 page scroll 与 viewer zoom 的交互冲突

这不是传统意义上的 FPS 优化，但它显著改善了交互效率和用户控制感。

## 5. 已实现的展示与体验优化

除了性能外，这一轮更有价值的一点是：组件已经完成从“能显示”到“可交付产品级展示”的过渡。

### 5.1 统一的产品化外观层

宿主侧已经补齐：

- 设置面板
- 元素图例
- loading overlay
- error / empty state
- 导出入口

这些能力把原始 3D runtime 包装成了面向业务页面的完整 viewer。

关键文件：

- `CrystalToolkitViewer.tsx`
- `CrystalStructureLoadingOverlay.tsx`
- `ViewerSettingsSelect.tsx`

### 5.2 服务端 Scene 与本地 Scene 双路径统一展示

当前支持：

- 直接消费 structure-service 返回的 Scene JSON
- 在浏览器本地由 site + lattice + polyhedra 构建 Scene

并通过统一的 `sceneData` 输出到同一个 `CrystalToolkitScene`，避免了双实现 UI。

### 5.3 多面体、原子半径与颜色方案的可视化一致性增强

通过：

- `applySceneVisuals()`
- `transformSceneJsonForViewer()`
- `structureSceneColors.ts`

已经实现：

- 元素颜色方案统一切换
- 多面体透明度统一收敛
- sphere 半径按模式成体系调整

这让 viewer 从“工程数据可视化”更进一步转向“材料结构展示系统”。

### 5.4 更清晰的加载态表现

`CrystalStructureLoadingOverlay` 已经从普通 spinner 升级为“球棍结构组装感”的加载表达，更符合晶体结构产品语义。

虽然它不是性能优化，但它提升了产品感、品牌感与技术叙事能力，适合在博客、汇报和软著材料里作为“展示系统设计”说明。

## 6. 目前仍然值得继续做，但尚未实现的优化

这一节故意单列，避免和已实现成果混淆。

### 6.1 多面体结果缓存

当前 `structurePolyhedra.ts` 仍会在本地 Scene 模式下按 `cifText + bondTolerance` 重新跑一次凸包构建。  
后续可以做：

- polyhedra 结果缓存
- 以 `cifText + bondTolerance` 为 key 复用结果

### 6.2 InstancedMesh / batching

对于大规模原子点和重复结构，仍有继续向：

- `InstancedMesh`
- sphere / cylinder batching

演进的空间。

这会是下一阶段更偏底层渲染重构的工作。

### 6.3 基于可见对象/相机状态的更细粒度按需渲染

当前静态场景已经比早期更收敛，但如果要继续压 CPU：

- 可以继续做相机静止时暂停某些非必要刷新
- 可以做更细的 dirty-flag 传播机制

### 6.4 浏览器本地多面体计算迁移到 Worker

当前多面体构建仍在主线程运行。  
如果结构规模继续扩大，后续可以考虑：

- 解析与凸包构建放到 Web Worker

## 7. 总结

如果把这次晶体展示组件的工作做一句话总结，可以概括为：

> 我们已经把晶体结构展示从“能渲染一个 Three.js 场景”，推进到了“具备稳定生命周期、较清晰模块边界、可控性能路径和产品化展示外观的结构可视化组件系统”。

本轮最值得强调的已实现成果不是某一个单点技巧，而是三类能力已经同时成立：

1. **运行时能力成立**：Scene、interaction、selection、inset、export 等主路径稳定。
2. **性能收敛能力成立**：全屏不重建、resize 收敛、outline dirty 化、viewport 配置下沉。
3. **产品展示能力成立**：宿主可配置、设置面板、图例、loading、导出和多种视觉方案已经完整闭环。

这使得 `matsci-crystal-viewer-kit` 不再只是一个“组件”，而更接近一个可持续演进的材料结构展示底座。
